# S4 보안 사고 - 고객사 API 키 유출과 비정상 호출

> 안전 규칙: **본인 서비스에만**, 데모 키와 본인이 발급한 키로만 시험했다. 유출 커밋은 과제 저장소가 아닌 임시 연습 저장소(`/tmp/s4p`)에서 만들었다.
> 새로 발급한 키는 화면·증거 파일·저장소에 남기지 않고 작업 VM 의 `~/.att-env`(권한 600)에만 저장했다. 마지막에 `gitleaks` 전체 이력 0건과 증거 파일에 실제 키 형식이 없음을 확인했다(`evidence/*s4-7-gitleaks.txt`).
> 시각은 2026-11-23 한국 시간(KST).

## 1. 상황 설정과 대응 목표 (4)

- **상황:** 고객사 2 의 API 키가 공개 저장소에 노출됐다. 이 서비스에서는 가정이 아니었다. 데모 키 `demo-key-tenant-1~3` 이 **k6 스크립트와 스모크 테스트에 평문으로 들어 있고 운영 서비스에서 실제로 동작**했다. 저장소를 본 사람은 누구나 고객사 직원의 출근을 대신 찍을 수 있었다. 유출된 키로 9시 출근 몰림 수준(최대 250 req/s)의 호출이 들어오고, 무작위 사번으로 출근이 찍힌다.
- **목표 (15분 안에)**
  1. 유출과 비정상 호출을 **탐지**한다.
  2. 해당 고객사 키를 교체하고 **이전 키를 차단**한다 (차단까지 걸리는 시간을 잰다).
  3. **다른 고객사 영향 0** 을 확인한다.
  4. 위조가 의심되는 출근 기록의 **범위를 식별**한다.
  5. 재발 방지책을 코드로 넣는다.

## 2. 재현 방법

```bash
# 1) 탐지: 연습 저장소에서 데모 키 / 실제 형식 키를 커밋하고 gitleaks 로 잡히는지
scripts/ev.sh s4-1-detect '...'            # evidence/*s4-1-detect.txt 에 명령 전체가 있다

# 2) 유출 키 폭주 + 같은 시간 고객사 1 정상 트래픽 측정
k6 run -q -e BASE=https://$SVC -e KEYS=demo-key-tenant-2 tests/load/k6-clock-rush.js &
API_KEY=demo-key-tenant-1 MODE=clock tests/failover/measure.sh https://$SVC 230

# 3) 키 교체 (data01, 새 키는 화면에 한 번만 출력 → ~/.att-env 로 바로 저장) 후 옛 키로 0.5초마다 요청해 401 까지 시간 측정
ssh -p 2205 ubuntu@$MGMT "sudo bash -s -- 2" < scripts/rotate-tenant-key.sh

# 4) 위조 의심 기록: 공격 시간대의 고객사 2 출근 기록
sudo -u postgres psql -d att -c "SELECT source, count(*), count(DISTINCT emp_no) FROM attendance WHERE tenant_id=2 AND ts BETWEEN '...' AND '...' GROUP BY source"
```

**처음부터 막혀 있던 것 (설계가 피해 범위를 줄인 부분)**
- **RLS:** 유출 키로는 고객사 2 의 데이터만 보인다. 공격 중에도 스모크의 분리 검사(대조군 포함)가 통과했다.
- **키 해시 저장:** DB 에는 SHA-256 해시만 있어 DB 가 유출돼도 키 원문은 없다.
- **고객사별 호출 제한(`limit_req`):** 다른 고객사 영향 0 은 RLS·제한과 함께, 앱이 연결 풀 이후 초당 250건을 여유 있게 처리한 덕분이기도 하다.

## 6. 포스트모템 (4)

**근본 원인**
1. **예측 가능한 데모 키가 운영 서비스에서 동작했다.** 연습용 시드 데이터가 실제 인증 수단이 됐고, 저장소에 평문으로 있었다.
2. **탐지 도구를 믿었지만 키 형식이 탐지되지 않는 모양이었다.** `demo-key-tenant-2` 는 무작위성이 낮아 gitleaks 기본 규칙에 안 걸린다.
3. **고객사 단위로 보는 지표가 없었다.** 전체 요청률은 9시 피크와 구분되지 않는다.

**잘된 점:** 피해가 한 고객사에 갇혔다(RLS·고객사별 제한). 키 교체가 DB 한 줄 수정으로 끝나고 30초 안에 반영된다. 키를 화면·증거·저장소에 한 번도 남기지 않고 교체를 마쳤다.

**아쉬운 점 / 알려진 한계**
- **호출 제한이 lb 마다 따로 센다.** VR 로드밸런서가 연결 단위로 나누므로 한쪽 lb 에 연결이 몰리면 그 lb 만 막는다. 고객사당 실제 상한은 lb 수 × 100 req/s 이고, lb 를 늘릴수록 느슨해진다. → 공유 카운터(Redis) 기반 제한이 필요하다.
- **기록마다 어떤 키로 찍혔는지 남지 않는다.** 그래서 위조 기록을 시간대로만 추정하고, 같은 시간의 진짜 출근과 구분하지 못했다.
- **전체 재생성하면 데모 키가 다시 살아난다.** 앱의 초기 데이터가 데모 키를 심기 때문이다(재생성 검증 `C-smoke` 에서 데모 키로 통과).

**재발 방지책**
