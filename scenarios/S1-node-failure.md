## 4. 조치와 설계 변경 (6)

| 변경 | 이유 (측정으로 확인한 문제) | 커밋 |
|---|---|---|
| DB 연결 풀 + 차단기 | 요청마다 새로 접속(TCP+SCRAM+fork)하던 비용. 풀만 넣으면 DB 장애 중 요청마다 풀 대기 → 차단기로 즉시 스풀 | `a2632cc` |
| `att_db_up` 지표, `DatabaseUnreachable`·`LbNginxDown` 경보, `AppBackendsDegraded` 15초 | 이중화와 스풀이 장애를 가려 **사용자도 운영자도 몰랐다**. nginx 만 죽으면 exporter 는 살아 있어 `up` 으로 안 보이고, DB 가 죽어도 5xx 가 안 나 오류율로 안 보임 | `a2dd04a` |
| 차단기 복구 판단을 백그라운드 확인(3초)으로 | 사용자 요청이 1초마다 DB 를 시험하며 기다려 장애 중 17~20% 가 0.5초 초과 | `3bd358e` |
| 백업 전용 역할 `att_backup`(읽기 전용 + BYPASSRLS, mon01 에서만), 실패 시 덤프 파일 안 남김, `BackupNeverSucceeded` 경보 | FORCE RLS 로 `pg_dump` 가 매번 실패, 8KB 깨진 파일이 15분마다 생겨 정상처럼 보였고 경보는 "성공 0회" 를 볼 수 없었다 | `9610586` |
| 스모크 분리 검사를 "퇴근 표식 + 대조군 + 키 유효 전제" 로 | 부하로 생긴 고객사 2 의 자기 기록을 누출로 오판 | `1d5947d`, `7b5cdca` |

**Terraform 관점:** 위 변경은 모두 `config/bootstrap/*.sh`, `config/prometheus/alerts.yml`, `config/grafana/`, `app/` 에 있고, `terraform/main.tf` 가 `file()` 로 읽어 cloud-init 에 넣는다. 운영 중 서버에는 `scripts/live/*.sh` 로 같은 내용을 반영했고, 마지막에 **destroy → apply 로 처음부터 다시 만들어 같은 결과가 나오는 것을 확인**했다(`evidence/*C-*.txt`: 스모크 10/10, 백업·복구 일치, 경보 15개, 대시보드 7패널). 콘솔에서 손으로 바꾼 설정은 없다.

**하지 않은 것과 이유:** DB 복제(data02)는 넣지 않았다. 스풀로 출근 접수(쓰기)는 DB 없이도 유지되고 유실이 0 임을 측정으로 확인했기 때문이다. 다만 DB 가 오래 죽으면 조회(현황·개인 기록)는 계속 실패하므로, 조회 가용성이 요구사항이 되면 복제가 다음 단계다.

## 6. 포스트모템 (4)

**근본 원인**
1. **이중화가 장애를 가렸다.** 사용자 피해가 0 이라 경보도 0 이었다. 경보는 "1분 이상 지속" 처럼 긴 장애만 보도록 짜여 있었고, nginx·DB 처럼 구성 요소별로 죽었는지 보는 신호가 없었다.
2. **장애 대응 코드가 스스로 지연을 만들었다.** 차단기가 복구 여부를 사용자 요청으로 확인해서, 장애 중 일부 사용자가 매번 1초씩 기다렸다.
3. **보안 강화(FORCE RLS)가 백업을 조용히 깨뜨렸다.** 파일은 계속 생겼고, 경보는 "마지막 성공 시각" 만 봐서 성공이 한 번도 없는 경우를 평가하지 못했다. 복구 리허설을 하기 전까지 아무도 몰랐다.

**잘된 점:** 측정 → 원인 → 수정 → 재측정을 같은 방법(measure.sh, 같은 40초)으로 반복해 전후가 직접 비교된다. 스풀 설계는 처음부터 유실 0 을 지켰고, 기준선 측정으로 그 가치(실패 48.9% → 0, 502 연쇄 차단)를 수치로 보였다.

**아쉬운 점:** 탐지 개선 후 app·lb 단독 장애는 다시 재지 않고 동시 장애로 대신했다. 스모크 테스트가 두 번 오판해 원인 확인에 시간을 썼다. 서버 시간대가 UTC 라 로그 대조가 번거로웠다.
